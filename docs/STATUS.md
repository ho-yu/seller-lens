## 1. 기획

- **한 줄 정의:** 상품의 리뷰를 넣으면 별점 분포와 실제 구매자가 말한 좋은 점·나쁜 점을 근거 리뷰와 함께 요약해, 소싱 판단에 쓸 상품 리뷰 리포트를 만든다.
- **판단은 내가 한다.** 도구는 추천·판정을 하지 않고 근거만 정리한다.
- **용도:** 직접 사용 + 포트폴리오.
- **기획의 변화**
  - 2026-10-02 (Day00): 셀러가 리뷰와 고객 문의에 대응하는 도구로 기획했다. 기능 F1~F9 (답글, CS 답변, 대응 큐 포함).
  - 2026-11-20: 소싱할 상품을 고를 때 리뷰를 요약해 보는 도구로 바꿨다. 답글·CS·대응 큐(F3·F4·F7)는 빼고, F8은 리포트에 흡수했다. 상품 비교(F10), 금액 계산(F11), 내 분류기(F12)를 확장으로 추가했다.

## 2. 설계

**전에는 없었다.** 강의 실습 단위로 함수를 만들어 `src/`로 옮겨 왔을 뿐, 데이터 흐름·저장 형식·모듈 구조는 정한 적이 없었다. [DESIGN.md](DESIGN.md)에 첫 초안을 썼다.

설계하면서 찾은 것 (지금 상태로는 리포트를 만들 수 없는 이유):

| 찾은 것 | 영향 | 설계안 |
|---|---|---|
| `reviews.csv`에 3점 리뷰(67건)가 없다 | 별점 분포가 틀린다 | 리포트용 `reviews_all.csv`를 따로 만든다 |
| `reviews.csv`에 `리뷰ID`가 없다 | 근거 리뷰를 원문으로 따라갈 수 없다 | `review_id`를 남긴다 |
| 태깅 스키마가 예전 방향이다 (불만 1개 + 긴급도) | 좋은 점이 없고, 리뷰 하나의 여러 불만을 못 담는다 | `pros`·`cons` 목록과 근거 문장 (v2) |
| 태깅 결과를 저장할 곳이 없다 | 2천 건을 매번 다시 태깅해야 한다 | `tags.jsonl`에 리뷰별로 저장 |
