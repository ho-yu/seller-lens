# sellerlens 기획서

> 상품 리뷰로 소싱 판단의 근거를 정리해 주는 나만의 리뷰 분석기. (작성: 2026-11-20)
> 2026-11-20 방향 변경: "이미 파는 셀러가 리뷰에 대응하는 도구"에서 "소싱할 상품을 고를 때 리뷰를 요약해 보는 도구"로 바꿨다. 답글·CS·대응 큐는 제외했다.
> 기능 상세는 [ROADMAP.md](ROADMAP.md), 장별 계획은 [CURRICULUM.md](CURRICULUM.md), 진행 현황은 [FEATURES.md](FEATURES.md).

## 1. 한 줄 정의

**상품의 리뷰를 넣으면 별점 분포와 실제 구매자가 말한 좋은 점·나쁜 점을 근거 리뷰와 함께 요약해, 소싱 판단에 쓸 상품 리뷰 리포트를 만든다.**

## 2. 왜 만드는가

- 소싱할 상품을 고를 때 실제 구매자의 리뷰가 가장 솔직한 정보다. 하지만 상품마다 리뷰가 수백~수천 건이라 다 읽을 수 없다.
- 평균 별점만 보면 놓치는 것이 있다: 5점인데 불만을 쓴 리뷰, 최근에 늘어난 불만, 특정 옵션에 몰린 불만.
- 그래서 리뷰를 무작위로 수집해 두고, 좋은 점과 나쁜 점을 숫자와 원문 근거로 정리해 본다.

## 3. 누가, 어떻게 쓰는가

- **사용자:** 나. 소싱 후보 상품의 리뷰 엑셀을 넣고 리포트를 읽는다. 본인 컴퓨터에서 로컬로 실행한다.
- **판단은 내가 한다.** 도구는 추천이나 판정을 하지 않는다. 판단에 쓸 근거를 정리해 보여 주는 데까지만 한다.
- **포트폴리오:** KANT에서 배운 것(LLM 호출, 구조화 출력, Tool Calling, FastAPI, LangChain, RAG, 평가)을 직접 구현한 결과물로 보여 준다.

## 4. 결과물: 상품 리뷰 리포트

아래 숫자와 내용은 모양을 보여 주려고 만든 예시다.

```
[상품 리뷰 리포트] 주방용품 A · 리뷰 1,000건 (2025.03 ~ 2026.11)

별점 분포   5점 62% | 4점 18% | 3점 8% | 2점 5% | 1점 7%   평균 4.2
감성        긍정 78% | 중립 9% | 부정 13%

👍 좋은 점                 언급 수   대표 리뷰
1. 세척이 쉽다              214건   "물로만 헹궈도 깨끗해요"
2. 가격 대비 튼튼하다       158건   "이 가격에 이 두께면 만족"

👎 나쁜 점                 언급 수   대표 리뷰
1. 코팅이 벗겨진다           61건   "두 달 쓰니 바닥 코팅이 일어남"
2. 손잡이가 뜨거워진다       34건   "장갑 없이는 못 잡아요"

⚠ 확인할 점
- 5점인데 불만이 있는 리뷰 23건
- 최근 3개월 부정 비율 9% → 18% (코팅 불만 증가)
- 옵션별: 28cm 옵션에 손잡이 불만 집중
```

- **숫자는 코드가 센다.** 건수, 비율, 추이는 pandas로 집계한다.
- **LLM은 읽기만 한다.** 리뷰마다 태그를 붙이고, 비슷한 좋은 점·나쁜 점을 묶어 이름을 붙인다.
- **모든 항목에 근거 리뷰가 붙는다.** 원문으로 따라갈 수 없는 문장은 리포트에 넣지 않는다.

## 5. 기능

| 구분 | ID | 기능 | 입력 → 출력 |
|---|---|---|---|
| 핵심 | F1 | 리뷰 통합·정제 | 수집한 엑셀 여러 개 → 개인정보·중복·빈 본문을 지운 표준 데이터 1개 |
| 핵심 | F2 | 리뷰 태깅 | 리뷰 1건 → 감성, 좋은 점 유형, 나쁜 점 유형, 근거 문장 (JSON) |
| 핵심 | F5 | 상품 리뷰 리포트 | 상품 하나의 리뷰 → 위 예시 리포트 |
| 확장 | F6 | 리뷰 근거 검색 | "코팅 불만만 보여 줘" + 상품·별점·옵션·기간 조건 → 원문 리뷰 |
| 확장 | F10 | 상품 비교 | 후보 2~3개 → 별점·좋은 점·나쁜 점을 한 표로 |
| 확장 | F11 | 금액 계산 | 원가·판매가·수수료·배송비 → 마진, 마진율 (LLM 없이 코드로) |
| 확장 | F12 | 내 리뷰 분류기 | 내가 라벨 붙인 리뷰로 학습한 작은 분류기 (아래 6절) |
| 확장 | F9 | 리뷰 어시스턴트 | 질문 하나 → 통계·금액 질문은 계산 도구, 근거 질문은 검색으로 분기 |

**제외 (2026-11-20):** F3 대응 우선순위 큐, F4 리뷰 답글 초안, F7 CS 문의 답변 초안은 판매를 시작한 뒤에 필요한 기능이라 뺐다. F8 판매 소구점은 리포트의 "좋은 점"에 흡수했다. Day05의 답글 프롬프트 기록은 남겨 둔다.

## 6. "나만의 모델"

| 층 | 내용 | 언제 |
|---|---|---|
| **핵심: 나만의 분석 기준** | 내가 정한 태깅 스키마(좋은 점·나쁜 점 유형) + 프롬프트 + 내가 라벨 붙인 평가셋 | 1과목부터 계속 |
| **확장: 내 분류기 (F12)** | 리뷰 임베딩 + 로지스틱 회귀로 좋은 점·나쁜 점 유형을 분류한다. LLM보다 빠르고 비용이 없다 | 4과목 4장(임베딩) 뒤 |

포트폴리오의 핵심 이야기: **LLM 태깅과 내가 학습시킨 분류기를 같은 평가셋에서 비교했다.**
LLM 파인튜닝은 라벨 데이터가 부족하고 강의 범위 밖이라 하지 않는다.

## 7. 강의 순서에 맞춘 단계

| 단계 | 끝나면 | 상태 |
|---|---|---|
| 사전 준비 | 엑셀 5개 병합, 개인정보 제거, 리뷰 2,076건 | 완료 (Day01, Day05) |
| 1과목 | **CLI:** 상품 엑셀 하나 → 리포트 v0 (별점 분포 + 좋은 점·나쁜 점 Top) | 진행 중. 5~7장 완료, 8장 Tool Calling 진행 (Day08) |
| 2과목 | **API:** 엑셀 업로드 → 일괄 태깅 → 리포트, 금액 계산 엔드포인트 | 예정 |
| 3과목 | 체인으로 안정화, 실패한 리뷰만 다시 태깅 | 예정 |
| 4과목 | 리포트 항목마다 근거 인용, 근거 검색, 상품 비교, 평가, 내 분류기 | 예정 |

날짜 대신 장 단위로 관리한다. 하루에 한 장, 주 3~4시간이 기준이다.

## 8. 완료 기준

| 기준 | 내용 | 현재 |
|---|---|---|
| 직접 사용 | 새 상품의 리뷰 엑셀을 넣으면 리포트가 나온다 | 없음 |
| 태깅 정확도 | 내가 라벨 붙인 리뷰 200건에서 좋은 점·나쁜 점 유형이 맞는 비율 | 미측정. 감성만 60건에서 정확도 0.88, 부정 재현율 1.00, 정밀도 0.81 (Day06) |
| 근거 | 리포트의 모든 항목에서 원문 리뷰로 따라갈 수 있다 | 없음 |
| 내 분류기 | LLM 태깅과 같은 평가셋에서 정확도·속도 비교 | 4과목 |

목표 정확도 숫자는 라벨 200건을 만든 뒤 정한다.

## 9. 원칙

| 원칙 | 이유 |
|---|---|
| 판단은 사람이 한다 | 도구는 근거를 정리할 뿐, 추천이나 판정을 하지 않는다 |
| 숫자는 코드가 센다 | LLM이 건수와 평균을 세면 틀린다 |
| 근거를 남긴다 | 원문으로 확인할 수 없는 요약은 믿을 수 없다 |
| 측정한다 | 라벨 붙인 평가셋으로 개선 전후를 숫자로 비교한다 |
| 개인정보는 지운다 | 리뷰어 이름·번호는 정제 단계에서 지우고, 로컬 LLM(Ollama)을 기본으로 쓴다 |

## 10. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 태깅이 틀리면 리포트 전체가 틀린다 (Day07: 품질 불만을 `배송`으로 태깅) | 라벨 200건 평가셋으로 정확도를 재고, 리포트에 대표 리뷰를 붙여 눈으로도 확인한다 |
| 평점 라벨이 정답이 아닐 수 있다 (Day06: 4점인데 내용은 불만) | 평점과 별개로 내용 기준 라벨을 직접 붙인다 |
| 리뷰만으로는 소싱을 판단할 수 없다 (가격, 마진, 판매량이 없다) | 리포트는 "리뷰 관점의 근거"라고 명시한다. 금액은 F11로 따로 계산한다 |
| 수집한 리뷰의 공개 | 원본 엑셀은 git에 올리지 않고, 포트폴리오에는 집계 결과와 익명화한 예시만 싣는다 |
| 작은 로컬 모델의 한계 (`qwen3:4b-instruct`) | 평가셋으로 확인하고, 부족하면 모델 교체·fallback을 검토한다 |
| 학습이 무거워 멈춘다 (Day03) | A 등급만 직접 코딩하고, 하루 한 장·질문 하나로 끝낸다 |
