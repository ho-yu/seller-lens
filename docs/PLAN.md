# sellerlens 기획서

> 상품 리뷰로 소싱 판단의 근거를 정리해 주는 나만의 리뷰 분석기. 리뷰 분류는 내가 학습시킨 모델로 한다. (작성: 2026-11-20)
> 2026-11-20 방향 변경: "이미 파는 셀러가 리뷰에 대응하는 도구"에서 "소싱할 상품을 고를 때 리뷰를 요약해 보는 도구"로 바꿨다. 답글·CS·대응 큐는 제외했다.
> 2026-11-20 목표 추가: 리뷰를 수집한 목적이 모델 학습이었으므로, **내가 학습시킨 리뷰 분류기(F12)를 확장에서 핵심 목표로 올렸다.**
> 기능 상세는 [ROADMAP.md](ROADMAP.md), 장별 계획은 [CURRICULUM.md](CURRICULUM.md), 설계는 [DESIGN.md](DESIGN.md), 진행 현황은 [FEATURES.md](FEATURES.md).

## 1. 한 줄 정의

**수집한 리뷰로 리뷰 분류 모델을 직접 학습시키고, 그 모델로 상품의 별점 분포와 좋은 점·나쁜 점을 근거 리뷰와 함께 요약해 소싱 판단에 쓸 리포트를 만든다.**

목표는 두 개이고 서로 이어진다.

| 목표 | 결과물 |
|---|---|
| **내 모델** | 리뷰 → 좋은 점·나쁜 점 유형을 분류하는, 내가 학습시킨 분류기 |
| **내 도구** | 그 분류 결과로 만든 상품 리뷰 리포트 |

## 2. 왜 만드는가

- 소싱할 상품을 고를 때 실제 구매자의 리뷰가 가장 솔직한 정보다. 하지만 상품마다 리뷰가 수백~수천 건이라 다 읽을 수 없다.
- 평균 별점만 보면 놓치는 것이 있다: 5점인데 불만을 쓴 리뷰, 최근에 늘어난 불만, 특정 옵션에 몰린 불만.
- 리뷰를 직접 수집한 이유는 **내 모델을 학습시키기 위해서**다. 이미 학습된 LLM에 묻기만 하면 "내가 만든 모델"이 아니다. 내 데이터와 내 정답으로 학습시킨 분류기를 만들고, LLM과 숫자로 비교한다.

## 3. 누가, 어떻게 쓰는가

- **사용자:** 나. 소싱 후보 상품의 리뷰 엑셀을 넣고 리포트를 읽는다. 본인 컴퓨터에서 로컬로 실행한다.
- **판단은 내가 한다.** 도구는 추천이나 판정을 하지 않는다. 판단에 쓸 근거를 정리해 보여 주는 데까지만 한다.
- **포트폴리오:** "직접 수집한 리뷰로 분류 모델을 학습시켜 LLM과 비교했고, 그 모델로 리포트 도구를 만들었다"를 보여 준다. KANT에서 배운 것(LLM 호출, 구조화 출력, Tool Calling, FastAPI, LangChain, 임베딩, 평가)을 직접 구현한 결과물이다.

## 4. 결과물: 상품 리뷰 리포트

아래 숫자와 내용은 모양을 보여 주려고 만든 예시다.

```
[상품 리뷰 리포트] 주방용품 A · 리뷰 1,000건 (2025.03 ~ 2026.11)

별점 분포   5점 62% | 4점 18% | 3점 8% | 2점 5% | 1점 7%   평균 4.2
감성        긍정 78% | 중립 9% | 부정 13%

👍 좋은 점                 언급 수   대표 리뷰
1. 세척이 쉽다              214건   "물로만 헹궈도 깨끗해요"
2. 가격 대비 튼튼하다       158건   "이 가격에 이 두께면 만족"

👎 나쁜 점                 언급 수   대표 리뷰
1. 코팅이 벗겨진다           61건   "두 달 쓰니 바닥 코팅이 일어남"
2. 손잡이가 뜨거워진다       34건   "장갑 없이는 못 잡아요"

⚠ 확인할 점
- 5점인데 불만이 있는 리뷰 23건
- 최근 3개월 부정 비율 9% → 18% (코팅 불만 증가)
- 옵션별: 28cm 옵션에 손잡이 불만 집중

분류: 내 분류기 v1 (평가셋 정확도 0.xx)
```

- **숫자는 코드가 센다.** 건수, 비율, 추이는 pandas로 집계한다.
- **분류는 내 모델이 한다.** 내 분류기가 아직 부족한 동안에는 LLM 태깅을 쓰고, 리포트에 어느 쪽으로 분류했는지 적는다.
- **모든 항목에 근거 리뷰가 붙는다.** 원문으로 따라갈 수 없는 문장은 리포트에 넣지 않는다.

## 5. 기능

| 구분 | ID | 기능 | 입력 → 출력 |
|---|---|---|---|
| 핵심 | F1 | 리뷰 통합·정제 | 수집한 엑셀 여러 개 → 개인정보·중복·빈 본문을 지운 표준 데이터 1개 |
| 핵심 | F2 | 리뷰 태깅 (LLM) | 리뷰 1건 → 감성, 좋은 점 유형, 나쁜 점 유형, 근거 문장 (JSON). **내 모델의 학습용 정답 후보를 만든다** |
| 핵심 | F12 | 내 리뷰 분류기 | 내가 검수한 정답으로 학습한 분류기. 리뷰 → 좋은 점·나쁜 점 유형 (아래 6절) |
| 핵심 | F5 | 상품 리뷰 리포트 | 상품 하나의 리뷰 → 위 예시 리포트 |
| 확장 | F6 | 리뷰 근거 검색 | "코팅 불만만 보여 줘" + 상품·별점·옵션·기간 조건 → 원문 리뷰 |
| 확장 | F10 | 상품 비교 | 후보 2~3개 → 별점·좋은 점·나쁜 점을 한 표로 |
| 확장 | F11 | 금액 계산 | 원가·판매가·수수료·배송비 → 마진, 마진율 (LLM 없이 코드로) |
| 확장 | F9 | 리뷰 어시스턴트 | 질문 하나 → 통계·금액 질문은 계산 도구, 근거 질문은 검색으로 분기 |

**제외 (2026-11-20):** F3 대응 우선순위 큐, F4 리뷰 답글 초안, F7 CS 문의 답변 초안은 판매를 시작한 뒤에 필요한 기능이라 뺐다. F8 판매 소구점은 리포트의 "좋은 점"에 흡수했다. Day05의 답글 프롬프트 기록은 남겨 둔다.

## 6. 내 모델 (F12)

### 학습 흐름

```
수집한 리뷰 2,085건 (본문 있는 고유 리뷰)
   │
   ├─ 학습용 ── LLM 태깅(F2) ── 내가 검수·수정 ── 정답 ── 분류기 학습
   │
   └─ 평가용 ── 별도 수집 669건에서 내가 직접 라벨 200건 (학습에 절대 섞지 않음)
                         │
                         └── 내 분류기 vs LLM 태깅, 같은 200건으로 비교
```

- **LLM은 정답을 만드는 도우미다.** 2천 건을 처음부터 손으로 라벨 붙이기는 어렵다. LLM이 먼저 태깅하고 내가 검수해 고친 것을 정답으로 쓴다.
- **평가셋은 처음부터 따로 둔다.** 학습에 쓴 리뷰로 채점하면 점수가 부풀려진다 (Day06에서 배운 것).

### 단계

| 버전 | 정답 | 모델 | 의미 | 언제 |
|---|---|---|---|---|
| v0 기준선 | 별점 (1~2점 부정 / 4~5점 긍정) | TF-IDF + 로지스틱 회귀 | 학습 → 평가 한 바퀴를 처음 돌려 본다. Day06 LLM 결과(정확도 0.88)와 비교 | `결정 필요` (강의 외 작업) |
| v1 유형 분류기 | LLM 태깅 + 내 검수 | TF-IDF + 로지스틱 회귀 | 리포트에 필요한 좋은 점·나쁜 점 유형을 분류한다 | 태깅 v2와 검수가 끝난 뒤 |
| v2 임베딩 분류기 | v1과 같음 | 리뷰 임베딩 + 로지스틱 회귀 | 단어가 달라도 뜻이 같은 리뷰를 묶는다. v1과 비교 | 4과목 4장 (임베딩) 뒤 |

- 모델은 작고 빠른 것부터 쓴다. scikit-learn이 이미 설치되어 있다.
- LLM 파인튜닝은 라벨 데이터가 부족하고 강의 범위 밖이라 하지 않는다.
- 별점 기준선(v0)은 리포트에 직접 쓰지 않는다. 별점은 원래 있는 정보라 맞혀도 새로 얻는 것이 없다. 학습과 평가를 한 번 해 보는 연습이다.

## 7. 강의 순서에 맞춘 단계

| 단계 | 도구 | 내 모델 | 상태 |
|---|---|---|---|
| 사전 준비 | 엑셀 5개 병합, 개인정보 제거, 리뷰 2,076건 | 학습 재료 수집 | 완료 (Day01, Day05) |
| 1과목 | CLI: 상품 엑셀 → 리포트 v0 | 태깅 v2로 정답 후보 만들기, 평가셋 200건 라벨 | 진행 중. 5~7장 완료, 8장 Tool Calling 진행 (Day08) |
| 2과목 | API: 엑셀 업로드 → 일괄 태깅 → 리포트, 금액 계산 | 2천 건 일괄 태깅, 검수, v1 학습 | 예정 |
| 3과목 | 체인으로 안정화, 실패한 리뷰만 다시 태깅 | 리포트가 내 분류기를 쓰도록 연결 | 예정 |
| 4과목 | 근거 인용, 근거 검색, 상품 비교 | v2 임베딩 분류기, 평가셋으로 LLM·v1·v2 비교 | 예정 |

강의 순서는 바꾸지 않는다. 날짜 대신 장 단위로 관리한다. 하루에 한 장, 주 3~4시간이 기준이다.

| 근거 | 리포트의 모든 항목에서 원문 리뷰로 따라갈 수 있다 | 없음 |
| 지금까지의 측정 | 감성만 60건에서 LLM 정확도 0.88, 부정 재현율 1.00, 정밀도 0.81 (Day06) | 있음 |

## 9. 원칙

| 원칙 | 이유 |
|---|---|
| 판단은 사람이 한다 | 도구는 근거를 정리할 뿐, 추천이나 판정을 하지 않는다 |
| 평가셋은 학습에 섞지 않는다 | 섞으면 점수가 부풀려져 모델이 좋아졌는지 알 수 없다 |
| 숫자는 코드가 센다 | LLM이 건수와 평균을 세면 틀린다 |
| 근거를 남긴다 | 원문으로 확인할 수 없는 요약은 믿을 수 없다 |
| 측정한다 | 같은 평가셋으로 LLM, 내 모델 버전별 개선 전후를 숫자로 비교한다 |
| 개인정보는 지운다 | 리뷰어 이름·번호는 정제 단계에서 지우고, 로컬 LLM(Ollama)을 기본으로 쓴다 |

## 10. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| **정답이 틀리면 모델도 틀리게 배운다.** LLM 태깅은 틀릴 수 있다 (Day07: 품질 불만을 `배송`으로 태깅) | LLM 태깅을 그대로 정답으로 쓰지 않고 내가 검수한다 |
| **유형별 예시가 적다.** 리뷰 2,085건을 여러 유형으로 나누면 유형마다 수십 건뿐일 수 있다 | 유형 수를 줄여 시작하고, 예시가 적은 유형은 "기타"로 묶는다. 부족하면 리뷰를 더 수집한다 |
| **데이터가 한쪽으로 치우쳐 있다.** 5점이 많고, 본문 있는 3점은 9건뿐이다. 수집한 행의 29%는 본문이 없다 | 3점 150건이 있는 보강 파일을 활용한다. 다음 수집 때는 본문 있는 리뷰만, 별점별로 고르게 모은다 |
| **상품 5개, 카테고리 2개뿐이다** | 다른 카테고리 상품에서는 성능이 떨어질 수 있다고 리포트에 적고, 필요하면 카테고리를 넓혀 수집한다 |
| 평점 라벨이 정답이 아닐 수 있다 (Day06: 4점인데 내용은 불만) | 유형 분류의 정답은 평점이 아니라 내용 기준으로 붙인다 |
| 리뷰만으로는 소싱을 판단할 수 없다 | 리포트는 "리뷰 관점의 근거"라고 명시하고, 금액은 F11로 따로 계산한다 |
| 수집한 리뷰의 공개 | 원본 엑셀은 git에 올리지 않고, 포트폴리오에는 집계 결과와 익명화한 예시만 싣는다 |
| 학습이 무거워 멈춘다 (Day03) | 작은 모델부터 시작하고, A 등급만 직접 코딩한다 |
