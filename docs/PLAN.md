# sellerlens 기획서

> README, ROADMAP, CURRICULUM, FEATURES, Day 일지에 흩어진 기획을 한 장으로 모았다. (작성: 2026-11-20, 초안)
> 기능 상세는 [ROADMAP.md](ROADMAP.md), 장별 계획은 [CURRICULUM.md](CURRICULUM.md), 진행 현황은 [FEATURES.md](FEATURES.md).
> `확인 필요`로 표시한 곳은 기존 문서에 근거가 없어 새로 적은 초안이다. 고치거나 지워도 된다.

## 1. 한 줄 요약

리뷰 엑셀을 넣으면 셀러가 매일 하는 일(리뷰 분류, 답글, 리포트, 고객 문의 답변)을 초안까지 만들어 주는 **개인용 도구**. KANT 강의 4과목을 순서대로 학습하면서 배운 것을 바로 구현한다.

## 2. 문제 정의

- 셀러는 상품마다 쌓이는 리뷰를 읽고, 불만을 분류하고, 답글을 쓰고, 상품별로 무엇이 문제인지 정리해야 한다.
- 특히 놓치기 쉬운 것: 평점은 높은데 내용에 불만이 있는 리뷰, 옵션·기간별로 몰리는 불만, 정책에 없는 고객 문의.
- 하루 리뷰 수와 처리 시간 같은 실제 수치는 아직 기록하지 않았다. `확인 필요`

## 3. 사용자

- 1인 셀러(나). 본인 컴퓨터에서 로컬로 실행한다. 로그인, 다중 사용자, 배포는 범위 밖이다.
- 모든 결과는 **초안**이다. 최종 확인과 등록은 셀러가 직접 한다.

## 4. 목표와 비목표

**목표**
1. 리뷰 엑셀 → 정제 → 태깅(감성·불만 유형·긴급도·근거 문장) → 우선순위 → 답글 초안 → 상품 리포트까지 한 흐름으로 쓴다.
2. 고객 문의에 정책·FAQ·리뷰를 근거로 출처와 함께 답하고, 근거가 없으면 보류한다.
3. 개선할 때마다 평가셋으로 전후를 숫자로 비교한다.
4. 강의 내용 중 기능에 꼭 필요하고 실무에서 자주 쓰는 개념만 직접 코딩한다 ([CLAUDE.md](../CLAUDE.md)).

**비목표** (자세한 이유는 [ROADMAP.md](ROADMAP.md) "추후 진행")
- 판매 채널 리뷰 자동 수집(크롤링·판매자 API), 답글·CS 답변 자동 등록
- 웹 대시보드(당분간 Swagger UI), 알림·주간 리포트 발송
- 사진 리뷰 분석, 파인튜닝, 경쟁 상품 비교, 영구 DB·배포, 멀티 에이전트

## 5. 기능 목적과 단계

**전체 목적:** 셀러가 (1) 어떤 리뷰를 먼저 볼지, (2) 어떻게 답할지, (3) 상품의 무엇이 문제이고 강점인지, (4) 고객 문의에 무엇을 근거로 답할지 **판단하는 데 드는 시간을 줄인다.** 판단과 등록은 셀러가 한다. 도구는 근거를 붙인 초안만 만든다.

| ID | 기능 | 입력 → 출력 | 푸는 문제 |
|---|---|---|---|
| F1 | 리뷰 통합·정제 | 상품·기간별 엑셀 여러 개 → 중복·빈 본문·개인정보를 지운 표준 데이터 1개 | 파일마다 컬럼과 형식이 달라 합치기 전에는 분석할 수 없다. 개인정보는 LLM에 들어가면 안 된다 |
| F2 | 리뷰 자동 태깅 | 리뷰 1건 → 감성·불만 유형·긴급도·근거 문장 (JSON) | 리뷰를 일일이 읽지 않아도 무슨 문제인지 안다. F3~F6의 바탕 데이터가 된다 |
| F3 | 대응 우선순위 큐 | F2 결과 → 오늘 볼 리뷰를 긴급도 순으로. 평점·내용 불일치 리뷰는 따로 | 5점인데 불만을 쓴 리뷰처럼 평점만 보면 놓치는 것을 잡는다 |
| F4 | 리뷰 답글 초안 | 리뷰 + 응답 정책 → 답글 초안 | 보상 확약 금지, 사실과 다른 내용 금지, 정해진 톤을 지키는 답글을 매번 새로 쓰지 않는다 |
| F5 | 상품 리뷰 리포트 | 상품·기간·옵션 조건 → 평점 분포, 불만 순위, 추이, 대표 리뷰 인용 | 건수와 평균은 코드가 세고 LLM은 해석과 요약만 한다. 상품의 문제를 한눈에 본다 |
| F6 | 리뷰 근거 검색 | 자연어 질문 + 상품·평점·옵션·기간 조건 → 원문 리뷰와 출처 | "열에 녹는다는 리뷰 있어?"처럼 근거가 되는 원문을 바로 찾는다 |
| F7 | CS 문의 답변 초안 | 고객 문의 + 상품 설명·교환·반품 정책·FAQ → 출처가 붙은 답변 초안 | 정책에 근거해 답한다. 근거가 없으면 지어내지 않고 "담당자 확인 필요"로 보류한다 |
| F8 | 판매 소구점 추출 | 긍정 리뷰 → 고객이 실제로 칭찬한 포인트·표현과 근거 리뷰 | 상세페이지·광고 문구의 소재를 고객의 말에서 얻는다. 과장 표현은 쓰지 않는다 |
| F9 | 셀러 어시스턴트 | 질문 하나 → 통계 질문은 집계 도구, 근거 질문은 RAG로 자동 분기해 답 | 기능마다 따로 찾지 않고 한 곳에서 묻는다 |

이 도구가 **하지 않는 것:** 리뷰를 자동으로 수집하지 않고, 답글·답변을 채널에 자동으로 올리지 않는다.

**단계**

| 단계 | 끝나면 | 기능 |
|---|---|---|
| 사전 준비 | 엑셀 5개 병합, 개인정보 제거, 학습용 리뷰 2,076건 | F1 기본 |
| 1과목 CLI | 파일을 넣으면 태깅·답글·리포트가 나온다 | F2 태깅, F3 우선순위 큐, F4 답글 초안, F5 리포트, F8 소구점 |
| 2과목 API | 같은 기능을 FastAPI로 쓰고 엑셀 업로드·일괄 처리 | F1 완성 |
| 3과목 LangChain | 같은 API가 체인으로 동작하고 실패해도 멈추지 않는다 | 전체 (retry, fallback) |
| 4과목 RAG | 리뷰·정책 근거를 출처와 함께 찾고 CS 답변 초안을 받는다 | F6 근거 검색, F7 CS 답변, F9 어시스턴트 |

F9는 질문을 둘로 가른다: "몇 건?" 같은 **집계 질문**은 집계 함수(Tool Calling), "근거를 보여 줘" 같은 **근거 질문**은 RAG.

## 6. 설계 원칙

| 원칙 | 이유 |
|---|---|
| 사람이 최종 확인한다 | LLM은 틀릴 수 있고, 외부 채널에 잘못 올라가면 되돌리기 어렵다 |
| 개인정보는 LLM에 보내지 않는다 | 이름·리뷰어번호는 정제 단계에서 지우고, 로컬 LLM(Ollama, `qwen3:4b-instruct`)을 기본으로 쓴다 |
| 근거를 남긴다 | 결과마다 근거 리뷰·문서를 붙이고, 근거가 없으면 답하지 않는다 |
| 측정한다 | 평점 라벨과 직접 만든 평가셋으로 개선 전후를 비교한다 |
| 집계는 코드, 해석은 LLM | 건수·평균을 LLM이 세면 틀린다 |

## 7. 성공 지표

| 영역 | 지표 | 현재 | 목표 (초안, `확인 필요`) |
|---|---|---|---|
| F2 감성 분류 | 부정 재현율·정밀도·정확도 (평점 라벨 평가셋) | 60건(2점 30·4점 30), few-shot 정확도 0.88·재현율 1.00·정밀도 0.81 (zero-shot 정확도 0.85) | 3점을 더한 큰 평가셋에서 재현율을 유지하면서 정밀도 올리기. 목표값은 평가셋이 커진 뒤 정한다 |
| F2 불만 유형 | 유형 정답과 일치하는 비율 | 미측정. Day07에서 품질 불만이 `배송`으로 틀린 사례 1건 | 먼저 정답 붙인 평가셋을 만든다 |
| 출력 구조 | 스키마 검증 통과율 | 스키마 지정 시 3/3 (3건 시험) | retry 포함 100% |
| F6 근거 검색 | Hit@k, Recall@k | 미측정 | 셀러 질문 20개 평가셋으로 BM25·Dense·Hybrid 전후 비교 |
| F7 CS 답변 | 출처 표시, 근거 없는 질문의 보류 | 미측정 | 모든 답변에 출처, 근거 없는 질문은 "담당자 확인 필요" |
